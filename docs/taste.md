# Кластеры вкуса: проверка

Что проверяли: даёт ли кластер похожих посетителей (по контексту, моторике из мини-игр и тому, что они открывали) лучший порядок выдачи, и не вредит ли там, где сигнала нет. Код: `app/taste.py`, `app/visitors.py`. Воспроизвести: `bench/taste_expedia.py`, `bench/taste_synth_bench.py`, `tests/taste_check.py`. Сырые результаты: `bench/results/taste_expedia.json`, `bench/results/taste_synth.json`.

## Итог

| Проверка | Результат |
|---|---|
| Реальные данные Expedia, формула приложения с постоянной силой λ = 0,6 | **вредит**: MRR 0,3458 → 0,2935 (−0,052, 95% ДИ [−0,053; −0,051]) |
| То же, λ выбирается по MRR на valid из {0; 0,02; 0,05; 0,1} | выбрано **λ = 0** (λ = 0,02 даёт ту же 0,3531): перестановка выключена, вреда нет |
| Expedia, вероятностное смешивание (log P(отель \| направление) + β·log подъёма кластера) | +0,0006 MRR (+0,17%, ДИ [+0,0004; +0,0009]); у новичков +0,0003, ДИ [−0,0004; +0,0009], **не значимо** |
| Синтетика, контроль без сигнала в контексте | новичкам **0** изменений в 9 из 9 прогонов: холодный повтор выбирает λ_cold = 0 (посетителям с историей помогает их собственная история, это отдельная λ_warm) |
| Синтетика, сильный сигнал (0,9), 1000 посетителей | MRR новичков +0,039 (0,2173 → 0,2566), значимо в 3 из 3 зёрен |
| Задержка `taste.apply` на 30 отелях | p95 ≤ 0,4 мс (макс. 0,36); обучение на 1000 посетителях ≤ 2 с (макс. 1,86) |
| Браузер (Playwright, телефон 390 px и десктоп) | до согласия ничего не отправляется; после «Учитывать» пишутся визит, поиск, выдача, открытие, время просмотра; «Не надо» = 0 записей; «Стереть мои данные» удаляет посетителя и события; с `?cluster=1` (только при `TASTE_DEMO=1`) порядок меняется, штамп «Демо: синтетические посетители»; без флага выдача прежняя; 0 ошибок JS |

Вывод: механизм работает и безопасен, но на реальных данных Expedia контекст без истории почти ничего не добавляет к сильному сигналу запроса. Поэтому в режиме `auto` после порога сила буста не задаётся руками, а выбирается офлайн-повтором на своих логах (по значимому росту MRR, отдельно для новичков и для посетителей с историей), и до порога всё работает в тени. Постоянная λ = 0,6 как сила для всех была ошибкой, её нашёл этот бенчмарк. Она осталась только там, где посетитель не видит её как настоящую подстройку: демо (`?cluster=1`, помечено на штампе) и расчёт теневого порядка для лога. Ручной `TASTE_MODE=on` без пройденного порога берёт самую слабую силу 0,05.

## Expedia (реальные бронирования)

Данные: Kaggle «Expedia Hotel Recommendations», разбивка по времени из зеркала `huggingface.co/datasets/anhvanhyx9/expedia-train-val-test`: train 2 424 706 бронирований (2013-01 → 2014-10), valid 264 638, test 263 331 (2014-11 → 2014-12), цель один из 100 кластеров отелей. Новички (первое событие пользователя) в test: 49 462.

База: популярность кластеров отелей в направлении поиска (аналог нашего запроса). Кластеры посетителей: k-means по контексту без истории (страна, регион, мобильность, канал, сайт, состав группы, пакет, срок до заезда, длительность, месяц), направление в кластеры не входит. k и λ (или β) выбираются на valid, отчёт на test, ДИ бутстрепом по событиям.

| Вариант | MRR все | MRR новички | MAP@5 все | Сдвиг MRR (95% ДИ) |
|---|---|---|---|---|
| База (популярность в направлении) | 0,3458 | 0,3385 | 0,3055 | — |
| Формула приложения, λ = 0,6 | 0,2935 | 0,2908 | 0,2481 | −0,0523 [−0,0533; −0,0513] |
| Формула приложения, λ по valid из {0; 0,02; 0,05; 0,1} (= 0) | 0,3458 | 0,3385 | 0,3055 | 0 |
| Вероятностное смешивание, k = 64, β = 0,25 | 0,3464 | 0,3388 | 0,3060 | +0,0006 [+0,0004; +0,0009] |
| Контроль для смешивания: кластеры перемешаны между событиями | 0,3444 | — | 0,3039 | −0,0014 [−0,0018; −0,0011] |

Почему формула приложения вредит: она прибавляет буст к позиции, а не к вероятности, и при сильной базе (популярность в направлении) кластерный подъём перебивает её. Контроль с перемешанными кластерами хуже смешивания, значит слабый сигнал в контексте настоящий, но он мал.

## Синтетика: сила сигнала × число посетителей

5 персон со скрытым вкусом (семья, пара на закат, командировка, экономный, тишина). `signal` — доля посетителей, чей контекст (устройство, ОС, сеть, регион, час, моторика) взят у их персоны; 0 — контроль. Метрика: офлайн-повтор холодного старта (k-fold по посетителям, вкус только из контекста и моторики), 3 зерна на ячейку, λ выбирается повтором из {0,05; 0,1; 0,2; 0,4; 0,6} или 0, если ни одна не значима.

| signal | посетителей | MRR база | сдвиг MRR | выбранная λ | значимо | ARI с персонами | силуэт |
|---|---|---|---|---|---|---|---|
| 0 | 100 / 300 / 1000 | 0,208–0,214 | **0 / 0 / 0** | 0 во всех 9 | 0 из 9 | 0,00–0,01 | 0,13 |
| 0,3 | 100 / 300 / 1000 | 0,213–0,234 | 0 / +0,005 / +0,007 | 0–0,6 | 3 из 9 | 0,12–0,22 | 0,18–0,19 |
| 0,6 | 100 / 300 / 1000 | 0,218–0,229 | +0,008 / +0,021 / +0,024 | 0–0,6 | 7 из 9 | 0,41–0,46 | 0,30–0,31 |
| 0,9 | 100 / 300 / 1000 | 0,211–0,217 | +0,013 / +0,038 / +0,039 | 0,1–0,6 | 9 из 9 | 0,78–0,85 | 0,44–0,46 |

Значения в ячейках: среднее по 3 зёрнам; MRR база, ARI и силуэт даны диапазоном средних по трём размерам. Силуэт в контроле в этом прогоне до 0,140, ниже порога 0,15. В прогоне до исправления полярности признаков (ниже) он доходил до 0,157 и был выше порога в 4 из 9 прогонов: один силуэт не защищает, решает повтор с ДИ.

Исправление полярности: в первой версии признак отеля брался по первому найденному булеву ключу, и «стройка рядом» означала её отсутствие (none_near). Теперь признак = выполнено ли условие характеристики по умолчанию (то же, что проверяет поиск), таблица выше пересчитана после исправления.

## Порог включения

`TASTE_MODE=auto`: в тени, пока не выполнено всё сразу: ≥200 реальных посетителей с открытием, силуэт ≥ 0,15, в повторе ≥30 посетителей и хотя бы один из двух повторов (новички: только кластер; с историей: свой вкус + кластер) даёт нижнюю границу 95% ДИ выше нуля. Сила для каждого режима своя (`lmax_cold`, `lmax_warm`), 0 значит «не переставлять». Синтетика в порог не идёт: тест `tests/taste_check.py` проверяет это и то, что без сигнала в контексте `lmax_cold = 0`, а при сильном сигнале порог открывается и перестановка идёт без демо-флага.

## После порога: контроль и честный повтор

Каждый 7-й посетитель (по vid) остаётся без буста, с ним сравниваем (то же при ручном `TASTE_MODE=on`). Сервер пишет исходный порядок до буста (`serp_base`); клиент через `/api/events` записать его не может. Повтор после порога берёт только клики контрольной группы: клики под бустом смещают повтор в пользу буста.

## Данные посетителя

Ничего не отправляется до согласия: внизу экрана «Учитывать» / «Не надо». После согласия хранятся устройство, ОС и браузер, страна, регион, город и тип сети по IP, часовой пояс, экран, сеть, домен referrer, а также поиск, показанный порядок, открытия и время просмотра. Сам IP не хранится даже хэшем. «Стереть мои данные» в подвале и галочка в О!ркаде удаляют посетителя и события; события, пришедшие после стирания, не пишутся.

## Ограничения проверки

- Значимость в синтетике без поправки на множественность: перебираются 5 значений λ, берётся лучшее значимое, поэтому рост слегка оптимистичен. Контроль (0 из 9) это ограничивает.
- ДИ на Expedia по событиям: у посетителей с историей несколько событий, поэтому ДИ для «все» узковаты; для новичков (одно событие) честнее.
- Формула приложения на Expedia воспроизведена по устройству: вкус там вектор подъёма по 100 кластерам отелей, а не косинус по признакам, поэтому λ = 0,6 там не в той же шкале.
- Expedia: кластеры отелей вместо отелей, нет моторики и показанных выдач, поэтому проверяется только контекстный блок.
- Синтетика доказывает механику и безопасность, а не эффект на людях: эффект появится в логах тени после порога.
- Тип сети по ASN грубый (по названию владельца). Гео по IP без баз db-ip пустое.
