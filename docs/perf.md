# Задержка чата: замеры по шагам

Профайлер: `agent.chat` через claude-cli, две фразы подряд на своих копиях базы (Q1 «Тихий номер с видом на закат…»,
Q2 «Еду с мамой, ей тяжело ходить в гору…»). Время в секундах, один прогон на шаг (шум подписки ±5 с).
Строки функций: суммарное время вызова в основном процессе; `search_hotels` внутри MCP-сервера профайлер не видит.

| Шаг | Q1 всего | Q2 всего |
|---|---|---|
| База (feat/hotel-verdict) | 54 | н/д |
| A. без переигрывания | 31.0 | 34.4 |
| B. кэш разбора | 27.2 | 33.1 |
| C. constraints от агента | 27.5 | 16.3 |
| D. компактные ответы | 24.0 | 17.7 |

## A. Без переигрывания

`llm.cli_agent` забирает `tool_result` из stream-json и кладёт в `trace[i]["output"]`. Карточки поиска берутся из
него, grounding переигрывает вызов только когда вывода нет.

| Функция | Q1 | Q2 |
|---|---|---|
| search.parse (параллельно с агентом, для гейта покрытия) | 6.5 | 7.1 |
| llm.cli_agent | 30.3 | 33.5 |
| grounding.ground | 0.6 | 0.8 |
| пересборка last_search | 0 | 0 |

## B. Кэш разбора

Таблица `parse_cache` в базе фактов (общая для процесса чата и MCP-сервера). Ключ: текст без регистра и лишних
пробелов, отпечаток публичных характеристик сессии (id, ключевые слова, поля, первая строка описания), промпт разбора,
модель, провайдер, сессия. Кэшируется только успешный разбор LLM, правилам кэш не нужен.

| Функция | Q1 | Q2 |
|---|---|---|
| search.parse (параллельно с агентом) | 5.3 | 7.5 |
| llm.cli_agent | 26.5 | 32.3 |
| grounding.ground | 0.6 | 0.6 |

Ограничение: агент переформулирует запрос («…едем в июле» → «…, июль»), поэтому вложенный разбор внутри MCP по
ключу чата промахивается (в обоих прогонах в кэше три разные строки). Кэш бьёт повторы и точные совпадения; на
вложенный разбор агента действует шаг C.

## C. Структурный поиск от агента

`search_hotels(constraints, month, base, missing)`: условия агента проверяются по реестру и вложенный разбор LLM
пропускается (`parsed.parser == "agent"`). Схема характеристик, полей, типов и единиц генерируется из реестра в
описание инструмента (`capcard.constraints_schema`). Эквивалентность разбора: `docs/parse_equivalence.md`.

| Функция | Q1 | Q2 |
|---|---|---|
| search.parse (параллельно с агентом) | 6.7 | 7.6 |
| llm.cli_agent | 26.8 | 15.7 |
| grounding.ground | 0.6 | 0.6 |

Разброс по прогону заметный: Q2 вышел заметно быстрее, потому что агент написал более короткий ответ. Выигрыш
шага C в том, что вложенный разбор (6-10 с внутри MCP) исчезает с критического пути, когда агент передаёт constraints.

## D. Компактные ответы

SYSTEM: топ-3 отеля, по каждому три строки (почему подходит с цифрами, главный минус для этого гостя, просьба при
брони), одна строка о том, что неизвестно, предложение показать ещё; 700-1000 символов. Правила про источники,
уверенность и честность не тронуты.

| Функция | Q1 | Q2 |
|---|---|---|
| search.parse (параллельно с агентом) | 8.8 | 9.4 |
| llm.cli_agent | 23.3 | 17.0 |
| grounding.ground | 0.6 | 0.7 |

Длина ответа (3 прогона Q1: 1512, 1085 и один сбой на 301 символ; Q2: 1244, 1217 символов) против ~2300 в базе. Во всех
полных ответах grounding: 0 неподтверждённых утверждений. Детерминированный бенч (`bench/run.py`, LLM_PROVIDER=none)
совпадает с `final.json` кроме времени (`ms_per_render` 91 → 84).

Итог по двум фразам: Q1 54 → 24 с, Q2 → 17.7 с. Оценка шума: один прогон на шаг, подписка Claude Code даёт разброс
порядка ±5 с, поэтому разницу между соседними шагами B, C и D нельзя считать измеренной; надёжны только убранные
повторы (A: два лишних разбора по 8.6 с) и длина ответа (D).

## Итог замеров (оркестратор, 2 прогона на сборку, 11 сценариев без №9)

| Сборка | Замечания фактчекера | Покрытие условий | p50 | p90 |
|---|---|---|---|---|
| до оптимизаций (feat/hotel-verdict) | 17 / 21 | 0,905 | 53 / 40 с | 75 / 72 с |
| A–D без страховки | 9 / 6 | 0,905 / 0,857 | 19 / 20 с | 34 с |
| A–D + страховки разбора | 3 / 7 | 0,952 | 24 / 20 с | 34 / 29 с |

Разбор запроса: вложенный разбор Opus совпадает сам с собой в 22 из 32 запросов, поэтому точное совпадение не мерило. Со страховками разбор агента расходится с вложенным в сторону строгости (9 из 26 запросов: меньше «подходит», больше «возможно»), мягче только в 1 (парковка и зарядка, итоговые числа те же). Пример перекоса: «работаю удалённо… тихо днём, хороший интернет» даёт 0 подходящих и 58 «возможно» против 36 и 22 у вложенного разбора, потому что пожелание «рабочий стол» стало обязательным. Более быстрые модели для вложенного разбора не окупились: Sonnet совпадает с Opus в 18 из 32 и быстрее на 1,5 с, Haiku в 10 из 32 и не быстрее.
